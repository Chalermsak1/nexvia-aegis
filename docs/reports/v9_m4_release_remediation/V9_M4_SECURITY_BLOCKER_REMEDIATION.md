## 1. Signed evidence-root amendment proposal — NOT APPROVED

**Threat/attack:** A valid ticket for relative `results/v9` does not designate the durable external directory. An operator or same-UID process could point a valid claim at an unintended, mutable, low-capacity, or disposable location. The launcher correctly fails closed for production today (`launcher.py:885–890`). Removing that check without binding the root would weaken authorization.

**Proposed interface:** Version a *new* signed ticket payload; retain the existing relative output leaf but add a required `durable_evidence_root` that is either (A) a canonical absolute path plus volume identifier and owner-approved retention record, or (B) an opaque owner-controlled storage ID with a fixed authenticated resolution procedure. The owner must select one representation, exact storage location, permissions, volume identity, capacity and retention policy. Reject v1 for production external-root mode; no implicit v1→v2 upgrade. Include the new field in RFC 8785 signed bytes and strict schema verification; compare it to the resolved existing nonsymlink root **before registration or claim**. Record comparison, ticket digest, nonce, device/inode identity and resulting output path in provenance. Fail closed on mismatch, path traversal, symlink, unavailable root, insufficient capacity, duplicate nonce output, or changed root identity. Never reinterpret the unsigned `target_output_root` field as authorization for an arbitrary absolute directory.

**Implementation after approval:** Update the contract, canonical ticket field set, strict verifier, signer and launcher together on an isolated development branch/worktree. Preserve external outputs on all failures. Add synthetic tests for absent/extra/altered signed root, mismatched volume/path, symlink swap, root disappearance, duplicate output, failure before claim, failure after claim and partial-output retention. Use temporary test keys/tickets only. Owner security review of the exact schema and threat boundary is required before coding the production path.

## 2. Wheel and runtime provenance proposal — TRUST SOURCE MISSING

**Threat/attack:** A mutable environment can install the right package *names and versions* with altered wheel bytes; an attacker can also alter installed files and their local RECORD metadata together. `uv.lock`/local RECORD checks and Python `-I` are valuable drift checks but are not independent package-origin authentication.

**Proposed trust chain:** Owner creates or authenticates a read-only/offline wheelhouse (or equivalent signed installation attestation) with exact wheel filename, platform tag, size and SHA-256 for the complete resolved dependency closure, including build tools and the project package. Pin that inventory outside the agent-writable checkout and bind it to the designated candidate SHA and lock digest. Before environment creation, hash every wheel archive against that inventory; reject extras/missing/wrong platform. Build a fresh candidate-specific venv from verified archives without network resolution or unapproved editable path. Verify exact interpreter binary/path/version, installed package set/version, installed file RECORD hashes and import origins under isolated `-I`; record the verified wheel inventory digest and venv identity in the preclaim evidence. If an editable install is retained, explicitly authenticate its exact checkout path and file tree rather than treating a `.pth` entry as package-origin proof.

**Required tests:** Synthetic modified wheel with same version, malicious RECORD update, extra/transitive package, import path escape, stale `.pth` pointing to source checkout, wrong interpreter, unavailable wheelhouse, wrong platform, and interrupted environment build. Each must fail before claim. Positive test uses a locally generated benign fixture wheel and a separately pinned fixture digest. Do not call this control complete until an independent owner trust source and reproducible clean environment are actually verified.

## 3. Replay rollback protection proposal — TRUST MODEL DECISION REQUIRED

**Threat/attack:** A same-UID actor can restore a previously valid local ledger snapshot, then replay a previously claimed nonce. File locks, fsync, strict JSON and inode checks prevent many accidental races/corruptions but cannot detect this rollback (contract:95–98,250–262).

**Owner-selectable trust boundaries:** (A) an owner-held offline nonce registry with dated signed checkpoints, (B) an append-only service/account whose write credentials are unavailable to the launcher UID, or (C) owner-controlled write-once media. The owner must choose which actor can append, verify, recover and revoke; no external service is assumed available. Before registration/claim/outcome, compare a monotonic sequence and previous-ledger digest to the independent checkpoint. Write a new signed/attested checkpoint for every state transition, with exact nonce, partition, ticket digest, ledger digest and result digest. If the witness is missing, stale, forked or rolled back, fail closed before claim where possible and preserve incident evidence. Never reset a stranded claim to unclaimed; recovery requires owner review and independently reconstructed history.

**Required tests:** Restore an earlier well-formed ledger, delete checkpoint, fork checkpoint chain, replay nonce after local rollback, concurrent claims, outage during preclaim check, outage immediately after durable claim, crash between ledger and witness writes, and owner-confirmed reconciliation. Assert no duplicate Holdout grant and no implicit reset. Only synthetic ledgers/nonces.

The final owner-controlled trust record should bind the full candidate SHA, signed Staging Manifest digest/version, evaluator, launcher module and entrypoint, signer, verifier, canonicalizer, runtime probe, ledger code, `uv.lock`, Python interpreter and approved wheelhouse/install inventory. It should also pin the public verification key's fingerprint and identify private-key custody **without containing the private key**. Current local hashes at `b91cc99` are in `V9_M4_STAGING_MANIFEST_DRAFT_UNAPPROVED.md`; they are observations only.

Preferred signing custody from contract:232–244 is an out-of-band key/hardware boundary. The owner must select the custody model, independently verify the signer/tool digests before any signing ceremony, and ensure the launcher sees a separately authenticated public-key fingerprint. The owner must also specify the independent trust source (offline record, signed release advisory, hardware token or appropriately protected repository attestation). A report written by the same mutable checkout is not sufficient to authenticate itself.

**Required tests:** synthetic wrong signer/launcher/verifier digest, substituted public key, mismatched candidate/manifest digest, altered evaluator after approval, mismatched wheel inventory and missing trust record. Each should fail before claim. Positive tests use disposable synthetic keys and an authenticated fixture record; never production keys/tickets.
